PRIOR MEDIUM FINDING (rearm could clear an expired fire_claim outside the per-job fire fence) — RESOLVED
- Evidence: cron/jobs.py:2062 now returns `_under_fire_fence(job_ref["id"], lambda: _with_job(job_ref["id"], apply))` instead of the bare `_with_job(...)`. `_under_fire_fence` (jobs.py:345–350) acquires `_fire_job_lock` and fails closed (returns False) if it cannot.
- Why this closes the race: the fire-claim-clearing predicate `_claim_is_live(job.get("fire_claim"), now, 300)` (jobs.py:2048) only clears when the claim is stale (>300 s). A live run keeps its durable claim fresh via the heartbeat, so it is not stale — EXCEPT during the synchronous-delivery window where the heartbeat is intentionally bypassed. In exactly that window the running owner holds `_fire_job_lock` (via `fire_claim_fence` → `_owned_local_fire_fence` → `side_effect_fence`, scheduler.py:2696–2699 area / jobs.py:353–364). rearm now contends for the same per-job lock and blocks until delivery releases it, so it can no longer clear a claim out from under an in-flight owner. Outside delivery the heartbeat refreshes the durable claim, so it is never simultaneously stale-and-unfenced. The fail-open path is gone.
- Test evidence: tests/cron/test_claim_job_for_fire.py:96 `test_rearm_oneshot_waits_for_inflight_fire_fence` holds `jobs._fire_job_lock(job_id)`, spawns a rearm thread, asserts it does NOT complete (`rearmed.is_set() is False`) and the stale claim is untouched while the lock is held, then asserts it completes and clears the claim after release. This is a correct serialization proof (cross-thread RLock blocking within one process; cross-process protection is the underlying flock).

LOCK-ORDER / DEADLOCK — CLEAN
- Ordering is consistent with the existing claim primitives: rearm now uses the same `_under_fire_fence(...)→_with_job(...)` shape as `claim_job_for_fire` (jobs.py:2511) and `heartbeat_fire_claim` (jobs.py:2520). Order everywhere is fire-fence → jobs-lock. No inversion introduced.
- The new `_local_fire_fence_holders_lock` is a leaf: in `_record_local_fire_fence` (scheduler.py:2577) it is acquired/released around the counter mutation only and is NOT held across the `yield`; in `_same_run_holds_local_fire_fence` (scheduler.py:2561-ish) it is acquired and released immediately. It is never nested under, nor holds, any other lock. No cycle is possible.
- Critically, the heartbeat thread's guard `_same_run_holds_local_fire_fence` takes only the leaf holders-lock, never `_fire_job_lock`. So while delivery holds the fire fence, the heartbeat check itself cannot block on it — this is what prevents heartbeat self-starvation against a delivery-held fence.

FAIL-CLOSED FOR GENUINE OWNERSHIP LOSS — CONFIRMED
- The durable-heartbeat bypass (scheduler.py:2455–2457) is active ONLY while this run's local fence counter is >0, i.e. only inside `side_effect_fence` delivery, during which the cross-process flock is also held. No legitimate takeover can occur in that window because every claim mutation (`claim_job_for_fire`, `heartbeat_fire_claim`, `rearm_oneshot`) now routes through `_under_fire_fence` and would block on the same flock. So skipping the durable check there does not mask a real transfer — there can be none.
- Once delivery releases the fence, the loop resumes real `heartbeat_fire_claim` calls with the same grace/monotonic logic. Test evidence: `test_ownership_loss_after_delivery_fence_still_fails_closed` (patch lines 237–286) drives `heartbeat` to return False after the delivery fence exits and asserts `mark_job_run` is NOT called and `finish_execution(..., success=False, error="Fire claim ownership lost; stale result was discarded.")` — genuine loss still fails closed and discards the stale result.

RESIDUAL RISKS (non-blocking)
1. Narrow heartbeat-vs-fence timing window (low severity, pre-existing character, strictly improved by this patch). `_owned_local_fire_fence` acquires the fire fence first and records the local-fence counter a moment later (after the `owns_claim` read). If the heartbeat thread wakes in that sub-millisecond gap it sees `_same_run_holds…`=False and calls `heartbeat_fire_claim`, which then blocks on the delivery-held flock and could time out at `_JOBS_LOCK_TIMEOUT_SECONDS`, yielding a false ownership-loss trip. Probability is very low (heartbeat cadence vs a microsecond window) and the bypass this patch adds is the mitigation for the broader version of this problem, so it is strictly better than the no-bypass baseline, not a regression. Optional hardening: set the local-fence counter before/at fence acquisition, or have the heartbeat re-check `_same_run_holds…` after a blocked fence acquisition before declaring loss.
2. `rearm_oneshot` return-type widening (low severity, intended hardening). When the fire fence cannot be acquired (no cross-process lock backend / timeout), rearm now returns the `_under_fire_fence` sentinel `False` instead of proceeding. This is the correct fail-closed behavior and mirrors `claim_job_for_fire`'s bool/dict return. Callers that treat the result by truthiness are unaffected (False is falsy like the existing None); only a caller doing a strict `result is None` check would need to also handle False. Worth a one-line note to callers but not a defect.
